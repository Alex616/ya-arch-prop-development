# Требования к внешним интеграциям сервисов «Умный дом»

## Контекст

PropDevelopment интегрирует с платформой партнёра следующие сервисы:

- **Интеллектуальный домофон** с биометрией (распознавание лиц)
- **Интеллектуальный шлагбаум** с распознаванием номеров автомобилей

Доступ к устройствам предоставляется через существующее мобильное приложение собственников. Витрина сервисов для собственика выступает единой точкой входа для всех внешних интеграций.

---

## 1. Требования к безопасности

### 1.1. Защита персональных данных (ФЗ-152)

**Биометрические данные**

- Изображения лиц относятся к специальной категории персональных данных (ст. 11 ФЗ-152)
- Обязательно получение письменного согласия пользователей на обработку биометрии
- Биометрические шаблоны хранятся исключительно у партнёра с применением необратимых преобразований
- PropDevelopment не хранит исходные изображения лиц, только результаты распознавания
- Обеспечить право пользователя на отзыв согласия и удаление биометрических данных

**Номера автомобилей**

- Номера автомобилей являются персональными данными
- Требуется согласие на обработку данных автомобиля
- Хранение номеров в зашифрованном виде
- Доступ к данным только авторизованным системным компонентам

**Общие требования ФЗ-152**

- Назначение оператора и ответственного за обработку ПД
- Актуализация документов (политика обработки ПД, согласия пользователей)
- Оценка рисков и применение мер защиты (УЗ 1-4 класса по ФСТЭК)
- Уведомление Роскомнадзора об обработке биометрии

### 1.2. Безопасность передачи данных

**Шифрование канала**

- Обязательное использование TLS 1.2+ для всех соединений (мобильное приложение ↔ API Gateway ↔ партнёр)
- Запрет слабых cipher suites (RC4, DES, 3DES, MD5)
- Certificate pinning в мобильном приложении для защиты от MITM-атак
- Валидация сертификатов с проверкой цепочки доверия

**Шифрование критичных данных**

- Биометрические данные и номера автомобилей шифруются на уровне приложения перед передачей
- Использование симметричного шифрования (AES-256-GCM) для данных
- Использование асимметричного шифрования (RSA-2048+ / ECC) для обмена ключами
- Токены доступа передаются только через защищённые каналы

### 1.3. Безопасность хранения

**Учётные данные партнёра**

- API ключи, сертификаты и секреты хранятся в централизованном Vault (HashiCorp Vault, AWS Secrets Manager)
- Запрет хранения секретов в коде, конфигурационных файлах, переменных окружения
- Автоматическая ротация учётных данных (не реже 1 раза в 90 дней)
- Разграничение доступа к секретам по принципу least privilege

**Биометрические шаблоны**

- Хранение только у партнёра с применением необратимых хеш-функций
- Невозможность восстановления исходного изображения из шаблона
- Изоляция хранилища биометрии от других систем

**Логи и аудит**

- Логирование всех операций доступа к ПД
- Хранение логов не менее 6 месяцев
- Защита логов от несанкционированного изменения
- Мониторинг аномальных паттернов доступа

## 2. Протоколы аутентификации и авторизации

### 2.1. Аутентификация пользователей

**OAuth 2.0 / OpenID Connect**

- Мобильное приложение использует существующие учётные записи PropDevelopment
- Authorization Code Flow with PKCE для мобильных приложений
- Access tokens с ограниченным временем жизни (15 минут)
- Refresh tokens для продления сессий (срок действия 30 дней)
- Идентификатор пользователя передаётся через JWT (ID token)

### 2.2. Аутентификация между системами (Machine-to-Machine)

**OAuth 2.0 Client Credentials**

- "API для партнёра" аутентифицируется на платформе партнёра через Client Credentials Flow
- Использование service account с минимальными правами
- Client secret хранится в Vault с автоматической ротацией
- Access tokens кешируются до истечения срока действия

**Mutual TLS (mTLS)**

- Дополнительный уровень защиты для критичных интеграций
- Двусторонняя аутентификация с использованием клиентских и серверных сертификатов
- Сертификаты выпускаются внутренним PKI или доверенным CA
- Срок действия сертификатов не более 1 года с автоматической ротацией

**Ротация учётных данных**

- API ключи и Client secrets ротируются каждые 90 дней
- Сертификаты обновляются за 30 дней до истечения срока
- Поддержка параллельного использования старых и новых credentials в переходный период
- Автоматизация процесса ротации с алертами при ошибках

### 2.3. Авторизация

**RBAC (Role-Based Access Control)**

- Определены роли: `собственник`, `арендатор`, `гость`, `администратор`
- Права доступа назначаются на уровне ролей
- Принцип least privilege: пользователь получает минимальные необходимые права

| Роль | Права роли | Группы пользователей |
| --- | --- | --- |
| `собственник` | открытие домофона и шлагбаума своего объекта; управление биометрией (регистрация/удаление своего шаблона); просмотр истории событий своего объекта; выдача доступа арендаторам и гостям | Собственники, приобретшие жильё у PropDevelopment |
| `арендатор` | открытие домофона и шлагбаума объекта, к которому привязан; регистрация/удаление собственной биометрии; просмотр истории своих событий (без событий других пользователей) | Арендаторы, которым собственник предоставил доступ через мобильное приложение |
| `гость` | однократное или временное открытие домофона/шлагбаума по ссылке/QR-коду; биометрия не регистрируется; доступ ограничен по времени (TTL задаётся собственником) | Посетители, которым собственник выдал временный доступ |
| `администратор` | управление всеми устройствами в рамках жилого комплекса; просмотр агрегированных логов событий; управление списками доступа и биометрическими шаблонами всех жильцов; настройка параметров устройств | Сотрудники управляющей компании (операционная команда ЖКУ) |

**Разграничение доступа к устройствам**

- Проверка прав доступа к конкретному домофону/шлагбауму на уровне API сервиса
- Маппинг пользователя к объектам недвижимости (квартира, парковочное место)
- Запрет доступа к устройствам других объектов
- Кеширование прав доступа с TTL для снижения нагрузки

**Объектно-ориентированная авторизация**

- Детализированный контроль на уровне объектов (квартиры, места)
- Проверка разрешений перед каждым запросом к партнёру

## 3. Схема взаимодействия систем

### 3.1. Архитектурные компоненты

**Уровень 1: Мобильное приложение PropDevelopment**

- Инициирует запросы на управление устройствами
- Принимает push-уведомления о событиях

**Уровень 2: Витрина сервисов для собственников **

- Проксирует запросы между приложением и партнёром
- Валидирует аутентификацию и авторизацию (OAuth 2.0, RBAC)
- Принимает webhook от партнёра

**Уровень 3: Платформа партнёра (Smart Home API)**

- Предоставляет API для управления устройствами
- Отправляет webhook о событиях на устройствах

**Уровень 4: Устройства (Edge)**

- Интеллектуальные домофоны (камера + биометрия)
- Интеллектуальные шлагбаумы (камера + распознавание номеров)

### 3.2. Потоки взаимодействия

#### 3.2.1. Исходящие запросы к партнёру

| Операция              | Метод и endpoint               | Назначение                                                                    |
| --------------------- | ------------------------------ | ----------------------------------------------------------------------------- |
| Открытие домофона     | `POST /api/v1/intercom/open`   | Передача команды на открытие замка домофона                                   |
| Регистрация биометрии | `POST /api/v1/biometry/enroll` | Передача зашифрованного изображения лица для создания биометрического шаблона |
| Открытие шлагбаума    | `POST /api/v1/barrier/open`    | Передача команды на открытие шлагбаума                                        |

#### 3.2.2. Входящие данные от партнёра

| Событие                         | Метод и endpoint                          | Назначение                                                                                            |
| ------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Звонок в домофон                | `POST /webhooks/intercom/call`            | Принимает событие звонка с видеопотоком для отправки push-уведомления пользователю (с HMAC-подписью)  |
| Распознавание лица              | `POST /webhooks/biometry/face_recognized` | Принимает результат распознавания лица домофоном для автоматического открытия двери (с HMAC-подписью) |
| Распознавание номера автомобиля | `POST /webhooks/barrier/plate_recognized` | Принимает результат распознавания номера для автоматического открытия шлагбаума (с HMAC-подписью)     |
| Событие открытия шлагбаума      | `POST /webhooks/barrier/opened`           | Принимает подтверждение открытия шлагбаума для обновления статуса в приложении (с HMAC-подписью)      |
